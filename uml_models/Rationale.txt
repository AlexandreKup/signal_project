Design Rationale: Medical Monitoring and Alert System
1. Alert Generation System
We decided to break down the system into two parts: finding problems and responding to them. The AlertGenerator does the work of looking at patient data and the AlertManager decides how to send out the alerts. For example the manager figures out if a situation is serious enough to call an emergency team or if it just needs an update at the nursing station. By keeping these two tasks separate we can change the rules for alerts without touching the code that sends out the notifications. This makes the whole system easier to take care of as the hospitals needs change.
2. Data Storage System
For storing data we chose a system that links DataStorage and PatientRecord together. This makes sure that medical records are connected to the storage container and do not exist on their own. If the storage is cleared the records are deleted too which prevents data from being left. We also set up a rule to get rid of old data, which is important for the system to work properly. This helps the system use memory efficiently and follow the rules for managing data.
3. Patient Identification System
The system for identifying patients is designed with security and traceability in mind. By separating the patients information from the validation process we created a layer of protection for the database. The IdentityManager acts as a repository and a security guard. If there is a discrepancy between new data and existing records it triggers an error protocol right away. This approach makes the identification system flexible and easy to integrate with hospital databases using APIs.
4. Data Access Layer
To make the system flexible we built the data access layer around a set of rules using the DataListener interface. This means the main logic does not care how the data is received. Now we use TCPDataListener for network traffic but if we need to switch to WebSockets or read from files we can change the implementation without rewriting the processing engine. We also added a DataParser to turn data into clean structured objects so the rest of the app always has consistent data to work with.
5. Design Patterns
To improve the systems scalability and maintainability we used four key design patterns.
- Singleton Pattern: We applied this to DataStorage and HealthDataSimulator to ensure that there is only one source of truth for patient data across the application. This prevents conflicts and provides an access point to these central components.
- Strategy Pattern: We separated the alert evaluation logic from the AlertGenerator using the AlertStrategy interface. This allows us to define and swap algorithms for monitoring Blood Pressure, Heart Rate and Oxygen Saturation. We can add medical triggers without changing the core generator logic.
- Factory Method Pattern: We set up an AlertFactory hierarchy to create specific Alert objects dynamically. This ensures that the AlertGenerator remains independent of the alert types being created.
- Decorator Pattern: We used AlertDecorator to add dynamic behaviors to alerts, at runtime. Specifically the PriorityAlertDecorator and RepeatedAlertDecorator allow us to add metadata to standard alerts without cluttering the base Alert class.
