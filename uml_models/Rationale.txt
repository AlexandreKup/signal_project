Design Rationale: Medical Monitoring & Alert System
1. Alert Generation System
We decided to split the alert logic into two distinct parts: detection and response. The AlertGenerator handles the heavy lifting of analyzing patient data, while the AlertManager is strictly responsible for how those alerts are delivered. For example, the manager decides if a situation is critical enough for an emergency team or if it just needs a standard update at the nursing station. By separating these "concerns," we can tweak our medical triggers or thresholds in the future without ever touching the code that sends the notifications. It makes the whole system much easier to maintain as hospital needs change.
2. Data Storage System
For data management, we chose a persistence model based on a composition relationship between DataStorage and PatientRecord. This ensures referential integrity: medical records are strictly dependent on the lifecycle of the storage container. If the storage is cleared, the records are wiped as well, preventing "orphaned" data. We also implemented an automated retention policy (applyRetentionPolicy), which is a key technical component for system viability. This allows the system to automatically purge old data, optimizing memory usage and ensuring we stay compliant with clinical data management regulations.
3. Patient Identification System
The identity system architecture focuses on security and data traceability. By decoupling the actual patient entity (HospitalPatient) from the validation mechanisms (PatientIdentifier), we�ve created a layer of abstraction that protects the central database. The IdentityManager acts as both a repository and a security guard; any discrepancy between incoming simulator data and our existing records triggers immediate error protocols. This modular approach allows the identification system to scale, making it easier to integrate with external hospital databases via APIs later on.
4. Data Access Layer (Ingestion)
To keep the system flexible, we built the ingestion layer around a behavioral contract using the DataListener interface. This means the core logic doesn't actually care how the data arrives�it�s "protocol agnostic." Right now, we�re using TCPDataListener for network traffic, but if we ever need to switch to WebSockets or just read from flat files, we can swap the implementation without rewriting our processing engine. We also included a DataParser to act as a bridge, turning messy raw strings into clean, structured objects so that the rest of the app always has consistent data to work with.
